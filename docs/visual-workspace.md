# Your local AURA workspace

Ask your agent: **“Open my AURA visual workspace.”**

Or run from the AURA folder:

```bash
python scripts/workspace_ui.py
```

The browser opens automatically. The terminal prints the local address. Keep that process running while using the view; Ctrl+C closes the view. This is an on-demand local app, not an installed service. AURA's existing Python requirements are sufficient; no Node build, cloud hosting, AURA account, new database, or frontend dependencies are required.

For a selected external workspace:

```bash
python scripts/workspace_ui.py --workspace /path/to/workspace --business-id my-business
```

The existing workspace selection is respected when `--workspace` is omitted. A single organization is selected automatically; otherwise choose the business. A new user names their workspace/business before the quick-setup welcome, using the existing setup/readiness path. Existing workspaces skip creation; the welcome shows the current workspace name and offers Change name through normal canonical editing. The display name can change without moving the underlying folder. Nothing else is invented to populate the screen.

## Start with one useful task

The main page brings four areas together, without a row of tabs:

- **Business & memory:** goals and saved context, with a panel for editing and reviewing the rest.
- **Saved files & media:** recent files and previews, with a searchable browser for all saved work.
- **Workflows & recipes:** two separate collections, each browsable by topic and subgroup. Search can find both from the overview, with results separated by collection. Workflow instructions and recipe guidance retain their original identities and source files; categories are navigation aids.
- **Recurring tasks:** a combined view of readable native Codex and Hermes schedules, independent of the selected chat app. Saved AURA monitoring plans remain separate from scheduled jobs.

**Settings → Adjust AI settings** opens app selection. The header keeps the notification bell and Settings. The request box shows the chosen model and effort, alongside **Chats** and **New chat**. Supported native connections reopen the exact host-owned conversation; New chat starts a separate native conversation on the next send while retaining the selected business and its saved memory. Copy-to-existing-chat connections remain handoffs. The header bell opens notifications. Settings hold appearance, the tour, API connections, business creation, folder location, and Customize this workspace.

Each area opens a detail panel and returns to the same overview. The same canonical records and persistence helpers remain authoritative.

Refresh rereads the files. Use Refresh to reread saved information. It does not claim live synchronization, complete machine-wide file discovery, verified tool access, or active scheduling simply because records exist. Unreadable canonical records produce a notice rather than silently meaning "nothing saved."

## Connect your AI

First use opens a short, dismissible setup: **name your workspace → welcome → choose your AI app → choose models and favorites → quick tour → welcome → continue to the homepage**. Each screen has one clear next step. Discovery reads local host metadata without model inference. The Codex connection uses its native model catalogue and supported efforts; catalogue membership is not proof of account entitlement. The chosen settings apply to this interface's conversations and do not rewrite global model preferences. The final welcome is local text and uses no model quota.

Continuing with Codex prepares project-local attachment: a small managed pointer in the workspace's `AGENTS.md` and a native `.agents/skills/viraltrac-aura/SKILL.md` pointer to the current bundled guidance. Existing user instructions are retained; conflicting/customized Skills are not overwritten. Native Skill discovery is checked through Codex. This is scoped to native chats opened from this workspace, not installation into every AI app or attachment from unrelated folders. When the workspace is the AURA product itself, its existing instructions and bundled Skill are reused. These pointers may need refreshing after moving the product or workspace; the business files remain portable.

Connection checks stay with AI connection setup. They read workspace files and native metadata, check the configured model, and use a native sign-in check where supported (Pi), without sending a model prompt. Each connected app has its own ready/error/not-checked indicator; more than two apps use a compact two-column layout on wider screens. An unused installed app is not listed as disconnected, and one app's failure does not mark the others disconnected. These checks prepare a request; they do not prove provider balance, quota or per-model entitlement. Saving an app/model checks the updated connection before the tour. The final screen reuses that result without probing again: it shows a local welcome credited to DeAngelo Scott, Continue, Back, and an optional **Help me get started** action. Back returns to the tour. A connection error replaces the welcome with its cause and remedy; **Fix connection** safely retries the checks and returns to app settings if attention is still needed. Only the explicit starter action sends a normal AI request using the chosen model and existing conversation. It asks one short question about what the user wants to accomplish, waits for an answer, and does not request research, deliverables, or file changes. Continue, name/model changes, favorites, appearance, and replaying the tour never automatically send a welcome. Services such as email, hosting or payments remain connected through the host when needed.

**Settings → Adjust AI settings** opens app selection, the model button opens model settings directly, and **Settings → Quick setup & tour** restarts the guided sequence. Escape or an outside click dismisses it; a saved draft stays in place. Dismissal does not claim a successful connection.

The supported starting set is **Codex, Claude Code, Pi, OMP, Hermes, and Antigravity CLI (`agy`)**. Supported apps remain listed when missing, with a needs-setup label; installed apps are detected and users sign in through the host. The Connect screen offers side-by-side help for first-time users (ChatGPT, Claude, and Google Antigravity download pages plus Check again) and people whose app is unlisted (copyable connection instructions). It does not install apps or create accounts automatically. An optional `--agent-file` remains available for advanced custom connections. Models come from Codex `model/list`, Claude Code initialization, Pi/OMP `get_available_models`, Hermes ACP session metadata, or `agy models`. Pi/OMP report thinking levels for the chosen model; Claude reports supported efforts when exposed by its version. Hermes ACP and the current Antigravity model listing do not report per-model effort tiers, so the UI uses **App default**, retaining choices built into the model's name. AURA does not invent supported tiers. Hermes metadata may prepare an empty native ACP session; it sends no model prompt. **Refresh choices** rereads catalogues after sign-in or configuration changes. Model choices apply to requests from this view without rewriting global settings.

The model screen shows only models reported by the selected AI app. Choosing Codex means Codex executes the request; selecting a model never silently switches to Pi, OMP, Hermes, or another app. First use starts with **All models**. Model provider filters use compact selectable pills, and live search narrows the scrollable list. Direct OpenAI, Anthropic, Google, and xAI connections are separate from OpenRouter. OpenRouter groups every model served through that gateway, regardless of its maker; local connections have their own group and custom/unidentified connections use Other. Provider filters can be combined. All matching entries are rendered in the bounded scroll area; there is no hidden result cutoff. The chosen model and supported effort appear below it, without a second model dropdown or a separate access/app selector.

Filters identify the connection supplying a model, while search also matches the model maker. Google Antigravity’s reported models use the Google group because Antigravity supplies that connection. Every model entry and the current selection show a source label for sign-in, a reported API connection, OpenRouter, local access, or the configured app. A provider connection with unreported authentication is labeled as a connection rather than assumed to use API billing. App-specific access jargon is omitted. Catalogue membership is not proof of entitlement, account balance, or server reachability. Discovery failures keep Refresh/Try again, LLM connections, and Back available; a stale page can offer Reload page. A metadata failure is described as a model-loading failure, not a failed welcome connection. Setup failures distinguish billing/credits, usage limits, credentials, provider/model access, service outages, network errors, unavailable models, and explicit filesystem failures. Native error events and failed-command diagnostics retain their cause until the server creates a brief safe message; the browser displays that classified result without reinterpreting it. Rejected OAuth refresh grants are reported as a required sign-in. Native replies retain setup verification markers until the server checks them; markers are removed only for display and saved chat views. An unconfirmed setup read is described as unconfirmed workspace access, rather than asserted file denial. Unknown failures retain a general message and direct users to their native app.

Favorites and per-native-app/model effort choices are retained in local preferences. Model provider filters apply to both All models and Favorites within the selected app. Filter choices remain unchanged when switching apps. Older maker filters migrate to their direct-provider equivalents without changing favorites or effort preferences. Filtering retains the current choice. Applying a different AI app starts a new native chat, while saved business context remains available. The warning names both the selected app and the app containing the current chat. The native app owns authentication, execution, permissions, and usage limits.
Standard npm launchers, executables, and existing PowerShell launchers are supported. Simple static Python forwarding batch wrappers are preserved without invoking a command shell. Other custom wrappers still need configuration; their behavior is not bypassed. These are version-dependent command adapters, not a claim of end-to-end compatibility with every host/account. An unlisted app can use the custom command path below when its supported interface meets that contract.

Onboarding should preferably open this view already connected to the agent the person is using. Do not switch them to Codex simply because it is installed. If the agent supports a non-interactive command, use the connection file below. Otherwise use that host's supported interface or explain the limitation. AURA attachment makes memory available to an agent; it does not give this browser page control over an arbitrary open chat or its app-only tools.

The request box uses the selected agent's real execution, authentication and permission mechanisms. The optional Codex connection starts a native session with `codex exec --json`, records its returned ID, and sends follow-ups through `codex exec resume` with the chosen model/effort. Native history is loaded through Codex's metadata interface and its own transcript. Full prompts, tool activity and model context remain in Codex; the UI displays user/assistant conversation without internal instruction packets, private reasoning, or the welcome's verification footer. Native session context is resumed rather than reconstructed from a shortened browser transcript.

Reopening restores the selected native chat. If its task is still running in this view's server process, the page reconnects without resubmitting it. Chats are scoped to the selected business and provide a command to open the exact conversation in its owning CLI. Appearance in a desktop sidebar remains host/version dependent. Full histories remain in native storage; moving AURA business files does not transfer another application's chat archive.

Pi/OMP use JSON-mode requests and exact `--session`/`--resume` IDs; native RPC returns the current conversation branch on reopen. Hermes uses its JSON event stream, exact `--resume`, and redacted session export. Claude Code uses JSON events, exact `--resume`, and its local native transcript. Antigravity uses `agy` JSON events and exact `--conversation` IDs, retaining full native model context. Its current CLI does not expose a history-read command, so AURA restores its saved user-visible display and labels that limitation; changes made separately in the native app may not appear here. No shortened browser history is used to reconstruct model context for these supported connections.

For native connections, a machine-local `chat-views/<id>.json` stores only the sanitized visible user requests and final replies, separate from preferences and portable business memory. It restores Antigravity's display and provides a labeled fallback when a native transcript cannot be read. Requests are saved before execution, including failures before Codex creates a chat. Failed requests offer Edit & retry and Fix connection; retry fills the composer and does not resubmit work automatically. Optional Details preserve a redacted native cause. It is not a second source of model context or an archive of tools/private reasoning. The custom stdin/stdout adapter remains less capable: no native IDs or model discovery, and its bounded browser conversation disappears on reload. Manual copy remains a handoff.

Connection selection, appearance, notification preference and recent activity receipts, tour dismissal and small native-chat references (business, ID, title, model, effort and status/times) are stored in a machine-local preference file under `%LOCALAPPDATA%/ViralTrac/Aura/` on Windows, or `$XDG_STATE_HOME/ViralTrac/Aura/` (default `~/.local/state/`) elsewhere, keyed by workspace location. It contains no credentials, commands, transcript, or canonical business memory. A selected built-in connection is rediscovered on restart; a configured connection still needs its `--agent-file` launch argument. A prior successful welcome does not verify a future login or another computer.

**Appearance:** Settings offers **System**, **Light**, and **Dark**. System is the default and follows changes to the computer's preference while the view is open. All three use the same interface.

New-user links use the supplied ChatGPT, Claude, and Google Antigravity download pages. Detection checks for a usable native command connection, not merely an installed desktop window; the unlisted-app instructions remain available for attachment help. The local-model setup link is omitted from that beginner section. The app-selection screen always shows **My AI app isn’t listed** and a button to copy connection instructions into that app; no extra disclosure or manual-request control is needed. Without an agent connection or an explicitly chosen manual fallback, sending a request first opens connection setup.

For the included Codex option, selection reuses CLI authentication without bypass flags. New connections use the host's workspace-write sandbox by default, with no extra file-edit checkbox. Existing explicit read-only preferences remain until a connection is saved again. Host permission and sandbox boundaries still apply. Requests can still encounter host permission/account limitations; a ready status is not proof of every possible model or tool action. See [official non-interactive documentation](https://learn.chatgpt.com/docs/non-interactive-mode) and [native host interfaces](https://learn.chatgpt.com/docs/app-server).

**Replies:** the request guidance asks for everyday language, useful outcomes, and simple save locations rather than internal record types, IDs, or validation receipts. It supplies the running Python executable for helper commands and preserves direct file access through native tools; it does not assume a `python3` command exists in the host shell. Messages show timestamps and reported model/effort where available. The conversation has its own compact scrolling area, keeping the business overview within reach. It opens at the latest messages and follows replies while at the bottom; reading earlier messages preserves the scroll position. While a request runs, the composer remains available. **Stop** ends the request’s local process tree; **Stop & send** first stops it, then sends the user’s correction as a follow-up in the same native chat. Stopping is not rollback or a resumable pause; completed file changes and already-started external operations may remain. No automatic retry is made. The UI shows elapsed time, public assistant text as the harness emits it, and a compact Activity list of the last 12 tool/status events. It never displays hidden reasoning, raw tool arguments or tool outputs. Hosts that emit fewer public events provide less detail. Status becomes Reply ready, Stopped, or Needs your attention. Normal follow-ups reuse the native conversation ID. Intentional stops do not generate failure notifications. Native token counts are session totals including cached input, not a price estimate. The header bell shows a red unread count and a compact list of recent completed requests or failures, with timestamps, links to the corresponding native chat, and Mark all as read. Read state is shared across open tabs and saved locally; the most recent 50 receipts contain app/status/time/chat IDs, without request or reply content. Successful onboarding welcomes do not generate redundant alerts. Notify me when away requests optional system permission only after a user click; it can be muted from the same panel. Background tabs share delivery ownership, suppress alerts while another workspace tab is active, group pending updates with a 30-second cooldown, and use quiet, replaceable system notifications without business or reply text. Stale activity is not replayed on enabling alerts or reopening the page. The inbox remains available if system notifications are blocked or unsupported. Closed-browser notification delivery is not promised. No push service or notification daemon is installed.

**Recurring tasks:** the view reads local Codex automation TOML files and Hermes cron JSON files (including profiles), with owner, model, cadence, status and next scheduled time when reported. This is a schedule inventory, not proof that every scheduler is awake. Hermes edits/pause/resume use its native CLI and reread the job; common daily, weekly and interval schedules have ordinary day/time controls, with a custom option for advanced schedules; unrelated task settings stay intact. Model changes use Hermes-reported choices and preserve provider routing. Codex currently exposes no schedule-management method in the installed app-server schema, so its edits use an explicitly labeled AI/native-app handoff. Moving between apps also requires the AI to confirm the replacement before pausing the original; it is not a silent scheduler migration. Other apps and externally stored/cloud schedules are not claimed to be discovered. Creating a task sends the request to the selected agent; it must confirm the real scheduler owner, task ID and next run. Saved monitoring plans remain business intent. No independent scheduler, daemon or replacement job store is created.

**Panels:** click outside a panel or press Escape to dismiss it. An outside click dismisses the top panel only. A drag that starts inside a panel does not accidentally dismiss it on release.

### Another agent

An agent can connect its supported non-interactive command with a small local JSON file:

```json
{
  "name": "My installed agent",
  "argv": ["/absolute/path/to/agent-command", "its-supported-stdin-option"]
}
```

Then launch:

```bash
python scripts/workspace_ui.py --agent-file /path/to/local-connection.json
```

This is a command invocation, not a provider protocol: it must accept the complete request on stdin, print only the final user-facing text to stdout, and return nonzero on failure. Tool/reasoning events belong on stderr or in the host; the view does not ingest them. Use the host's documented options, not the placeholder option above. A Windows npm command should be invoked through its actual executable/Node entry point, not a command-shell string. `argv` is executed without shell interpolation. An optional `model` string is a configured label, not independent discovery of the runtime's model.

Keep this machine-specific connection file outside the portable business files, or in the ignored `.businessos/environments/` area. Do not put keys, tokens, passwords, shell scripts, or user prompts in argv. Credentials remain with the agent. AURA does not implement OAuth, provider accounts, a router, or a general tool registry.

The local app runs one task at a time. A task can use whatever actual tools this host connection exposes; a desktop app can expose additional app-only capabilities. Its final reply is not independent proof of publication or business results. Closing a tab does not cancel its task while the local server is running. Closing/restarting the local server is not a verified cancellation or guarantee of continued host work. A chat left working is identified as needing a check in the host, rather than automatically retried. Use the host to inspect/cancel interrupted work before retrying.

## Optional API connections

**Settings → API connections** accepts keys for OpenAI, Anthropic, Google Gemini, xAI/Grok, OpenRouter, Kie AI, fal.ai, Higgsfield, and ElevenLabs. **Other service** accepts a name and documented secret environment variable. These are convenient presets, not a capability registry or a provider allowlist for ordinary AURA work. Codex is an AI app using OpenAI or its configured provider; OpenRouter is a provider gateway. OpenCode is a separate AI app.

Keys can be kept **for this session only**, or encrypted for the current Windows user using CurrentUser DPAPI in `%LOCALAPPDATA%/ViralTrac/Aura/api-keys.bin`. No plaintext fallback is used. macOS uses Keychain. Linux uses the available Secret Service keyring through `secret-tool` when a desktop D-Bus session is present. Session-only keys remain available if no protected backend exists or a keyring is locked; normal host-owned credentials continue to work. Keys never fall back to a plaintext file. Protected keys belong to the current OS user and do not travel with business files. Processes running as that Windows user may access them. Removing a key here does not revoke it at the provider or unset externally configured environment variables.

The local server supplies keys as environment variables to agent processes launched here. Requests mention only service names and variable names, never values, so the agent can use appropriate documented APIs through its real tools. Read APIs do not return saved key values. Key fields are cleared after submission and dismissal. Browser storage, preferences, business memory, command arguments and access logs do not contain saved key values. The app redacts saved values from replies it displays; the host still owns its tool execution/logging, and agents must not print secrets. Keys are not installed globally or automatically attached to an unrelated already-open app.

Saving a key makes no provider request and displays **Not verified**. The first useful operation establishes actual access. Keys do not silently rewrite app provider routing or ensure that a subscription sign-in can use API billing; the host decides its authentication precedence. Native model discovery is refreshed after changes. This adds no AURA cloud account, API proxy, generation loop, or scheduler.

## Portable data and customization

The browser is optional. CLI helpers, native AI apps, and other harnesses continue to use the same files and the existing setup, doctor, retrieval, and persistence entry points. They do not need this UI, its connection checks, or its local preferences. An agent performing setup outside the browser uses `SETUP-WITH-AI.md` and the host's own Skill/instruction mechanism. An on-demand interface process must be open only when using the interface; it is not required for ordinary AURA use.

Business memory remains in the ordinary AURA workspace. The interface uses the existing persistence helpers and validation. It does not mirror business memory or scheduler state. Native chats remain host-owned; local display copies and optional protected/session API keys remain outside portable business memory.

The tour reminds people: **This is your workspace. You own the files and control how it works. Ask your AI to change the layout, add a view, or simplify something whenever you want.** Settings → Make this workspace yours prepares that request without starting another model call.

The standard visual assets live in `interface/`; the launcher is `scripts/workspace_ui.py`, with the optional native Codex helper in `scripts/workspace_codex.py`. To customize an individual business, ask the agent to copy the three visual assets into an organization-owned folder outside product source, adapt them, and open them with `--interface-dir /path/to/custom-interface`. The copy uses the same small local API and existing workspace/helpers; retain the token placeholder in its HTML, connection controls, and chat restoration. Keep relative file references where possible. Product upgrades leave this custom folder alone. Retain the standard interface as a working starting point. AURA does not need the custom view to keep operating.

The server listens only on `127.0.0.1`, checks the local Host/Origin, and protects file/state APIs and mutations with a per-launch token. Other business namespaces, hidden configuration, secrets, and paths escaping the selected workspace are excluded. Asset previews are bounded and do not execute saved HTML, SVG, or scripts. The browser UI itself loads no third-party assets. Using a cloud agent can still send permitted context to that agent under its normal policies; local storage does not imply local model inference.

For a browsable document view instead of an app, the existing `scripts/generate_knowledge_layer.py` helper remains available.

The model screen opens a language-model-only view of the same API connections form and protected store as Settings. OpenAI, Anthropic, Google, xAI, OpenRouter, and user-added LLM services belong here. Kie AI, fal.ai, Higgsfield, ElevenLabs, and other tool services remain in general Settings. Custom services can be classified as model providers when added through this view; this UI distinction does not constrain the host’s tools.

A key saved during onboarding appears in Settings with its original session/computer storage choice. Back to models refreshes the selected app’s catalogue after a key changes. A provider appears when a compatible host reports its models; saving a key alone neither verifies the account nor installs/configures a host. Local models appear when the selected app reports their configured connection. A bare model file or an unconfigured local server still needs a host connection; the UI does not create another local-model runtime. No global provider routing, host preferences, or credentials are silently rewritten.


## Linked files and folders

Use **Add files or folder** in Saved files & media. Choose a local file/folder with the native picker, or paste its full location, and optionally name it. The original stays in place. Linked locations can be filtered and searched with saved workspace files; previews and Copy file location resolve the real original. Unlinking removes only the reference. Missing locations remain visible for reconnection.

Links are explicit, business-scoped, read-only locations for the view, stored in machine-local preferences. Each request from this view includes their names/locations so the selected AI can read what helps the task using its normal permissions. Linking is not an upload, a whole-computer index, or automatic ingestion of every file into canonical memory. A native chat launched separately is not automatically given this machine-local list; ask the AI to remember a useful Asset/reference in canonical AURA memory when that broader reuse is wanted. After moving computers, reconnect local paths. Business files and existing CLI/native-app use remain independent.

Traversal, unselected roots, private settings/credential paths and links into another business are rejected. Hidden/private files are excluded. Browsing is bounded to 1,000 workspace files and 1,000 linked files; a limit notice directs the AI to search original folders when needed. The footer's local/privacy wording refers to workspace storage; its tooltip clarifies that AI requests still go to the user-selected app/provider.


## Choose a workspace

The workspace selector beside AURA is always visible, even with one workspace. It lists saved business/project spaces in the current AURA data folder and offers Add a workspace. The setup welcome uses the same list. Switching changes the business context, native-chat selection and linked locations, and updates the page URL so reopening preserves the selection. Unsaved browser drafts stay with their selected workspace. Add a workspace creates another separate business/project space using the existing AURA setup helper; it does not move the data folder or create a new physical storage root. Connected-app settings remain machine-local; only apps actually connected or used in prior native chats enter the status list. A status check never creates a model conversation.


## Open, update, back up, and restore

**Settings → Add or open a workspace → Open saved work** opens a saved workspace or an older AURA product folder. AURA follows that folder's saved workspace pointer, verifies readiness, and then selects it for the current installation. Recent locations are offered without scanning the computer. The name/business selector still switches businesses within the selected data folder. A new release can reuse existing business files through this same Open existing workspace action; it does not automatically overwrite an older product or merge incompatible records. Existing data remains in place. Native chats, linked locations and local preferences belong to their original workspace location; account sign-ins remain host-owned.

The combined workspace screen also creates a new business/project space through the existing setup helper. The top workspace selector uses that same Add or open action.

**Settings → Back up or restore → Create backup** saves a ZIP into the chosen folder outside the product/workspace. It covers the existing migration helper's organization-owned `instances`, `knowledge`, `attachments`, and `runtime` areas. Every file hash is checked and source changes abort publication. Machine API keys, app sign-ins, local preferences, externally linked folders, and custom files outside those areas are separate; preserve them through their normal mechanisms. Keep private backups in a location you trust.

Expand **Restore a backup**, choose the ZIP and a new or empty folder, then Restore backup. AURA verifies the file list, safe locations and hashes in staging before copying to the destination. It refuses to overwrite an occupied folder. Open restored workspace checks readiness and switches explicitly. The original workspace and backup remain intact. No hosted backup service, scheduler or updater is added.

## Native connection refinements

When an app's command is missing, its connection screen shows that app's official setup link and the missing installation/sign-in step. After installation, Check again refreshes discovery; a launcher may need reopening to inherit a changed PATH. Desktop installation alone is not treated as a working command connection. API-key entry alone does not install/configure an app or establish provider entitlement.

Connection saves prepare workspace-local instructions for Claude Code (`CLAUDE.md`), Pi/OMP (`AGENTS.md`), and Hermes (its selected supported project context file). Only the small marked AURA pointer is added/refreshed, retaining user content. Linked instruction files and incomplete managed blocks are not overwritten. These pointers are prepared instructions, not a claim that the host loaded a Skill; check through the host when needed. Codex retains its native Skill discovery check. Antigravity retains explicit request guidance where a documented project attachment cannot be established. Nothing is installed globally.
