# Your local AURA workspace

Ask your agent: **“Open my AURA visual workspace.”**

Or run from the AURA folder:

```bash
python scripts/workspace_ui.py
```

The browser opens automatically. The terminal prints the local address. Keep that process running while using the view; Ctrl+C closes the view. AURA's existing Python requirements are sufficient; no Node build, cloud hosting, AURA account, new database, or frontend dependencies are required.

**Settings → Startup & updates → Start AURA when I sign in** optionally launches the view quietly with this workspace. It is off by default and applies only to this computer. Windows uses a user Startup shortcut, macOS a user LaunchAgent, and Linux desktop sessions an XDG autostart entry. Saving the setting does not start AI work or enable another app's gateway. Open the bundled launcher anytime to see the running view; repeated launches reuse it. Disable the setting to remove AURA's unchanged login entry. Moving/deleting the AURA folder requires updating/disabling the entry; it is not part of portable business memory. macOS/Linux entry formats are covered by isolated checks; actual login behavior still needs native-machine verification.

Closing the browser tab hides the view. **Settings → Quit AURA** stops the local interface; **Restart AURA** closes and reopens it on the same address and workspace, loading saved updates. Both refuse while an AURA request is working; stop or finish that request first. Neither action stops independent AI-app gateways/schedules, changes login startup preferences, or deletes business files. Reopen the launcher to return after quitting.

**Settings → Startup & updates** shows your installed version, available release notes, and **Update now**, **Later**, or **Skip this version**. **Notify me** is the default. Optional automatic updates wait until idle; **Manual only** checks only when requested. The bell shows a version notice without forcing a popup. Native bundled apps download and verify the correct platform bundle in a separate local folder, reopen this workspace at the same address, and retain the old app for recovery. Your original launcher follows the working version. Git checkouts, customized app files, or changes requiring a workspace migration use manual guidance instead. Custom views and business data stay separate. See [update and recovery details](provenance-and-updates.md).

For a selected external workspace:

```bash
python scripts/workspace_ui.py --workspace /path/to/workspace --business-id my-business
```

## Find and keep your saved work

Normal launchers reuse the last selected workspace, even from a fresh AURA download. Explicit workspace arguments/environment settings and existing older application links take priority. New UI workspaces default to the operating system’s Documents folder under `AURA Workspaces/<business-name>/`; users can choose another parent folder. This changes the visual launcher default, not ordinary CLI workspace resolution or the supported one-folder deployment profile.

**Add or open a workspace** shows saved work found through recent locations, the default workspace area, Downloads, Documents and Desktop. Discovery reads recognizable AURA metadata with a bounded search, skips application internals and directory links, and never creates/moves/merges business data. Choosing a parent download folder, an older application folder with a workspace pointer, or an internal business folder resolves to a preview of the actual workspace. Real path aliases are deduplicated; distinct copies sharing a business ID/name remain separate. Opening still checks readiness before switching. A missing last workspace offers Find folder rather than silently creating a replacement.

**Create a new workspace** creates a separate durable folder and business. Existing businesses sharing one legacy workspace remain supported. **Change where this workspace is saved** copies and verifies workspace data, then reconnects to the destination; it refuses nonempty/nested targets and retains the original. Managed native instructions refresh to the current product, while custom instructions remain. Same-computer native chat references remain available as history in their original folder; new work starts a new native chat in the destination. This respects harness project boundaries. Provider-owned histories and scheduling runtimes do not become portable AURA state. Visual selection is remembered outside product source without rewriting its CLI workspace pointer.

The shared AGENTS/Skill guidance recommends `attachments/<business-id>/work/` for new outputs and workspace-relative Asset file references, unless the user selects another location. This applies to native apps/CLIs as well as the view. Saved Assets are recognized directly by the file view, including legacy deliverables and explicitly referenced external files/folders; they do not need a second registration through the UI. Missing files and linked folders offer Reconnect. Folder repair updates matching selected-business Asset paths while preserving their identities and other metadata. AURA is not a machine-wide file watcher and cannot automatically classify unrelated/unrecorded files.

Backups include workspace-owned files, legacy output folders, referenced local artifacts, and `.businessos/view.json` (portable file links, appearance and model favorites). Private application settings, known secrets, caches, dependencies and native account/chat/scheduler stores stay separate. The preview shows file size/count, exclusions, and linked locations. **Include files from linked locations** bundles permitted external originals and rewrites only the archive’s references into local attachments; it never moves the originals. Missing/excluded references remain visible. Restore verifies the archive into a new/empty folder, preserves file links and normalizes known local Asset paths from the original root. Older version-1 workspace backups remain supported.

Portable view data is an ordinary workspace file; routine local notification/chat receipts do not overwrite it. The last chosen folder, native chat handles, account keys and startup registration remain machine-local. Native/CLI workspace discovery is also available as `python scripts/workspace_catalog.py --current --json` or `--path <folder> --json`. Ordinary work still uses the existing AURA persistence helpers; the UI adds no separate memory or scheduling authority.

The existing workspace selection is respected when `--workspace` is omitted. A single organization is selected automatically; otherwise choose the business. A new user names their workspace/business before the quick-setup welcome, using the existing setup/readiness path. Existing workspaces skip creation; the welcome shows the current workspace name and offers Change name through normal canonical editing. The display name can change without moving the underlying folder. Nothing else is invented to populate the screen.

## Bring existing work together

**Settings → Add or open a workspace → Bring existing work together** opens one review flow. Choose a starting workspace, select additional saved workspaces or project folders, and choose a new destination. The starting business identities stay stable. Additional businesses can remain separate or be explicitly grouped with a starting business. A matching name/ID is navigation help; the review makes the grouping visible before applying it. Application-only downloads remain separate from business data.

**Review before combining** inventories all selected original files, estimates required space, compares content, and records excluded items. It makes no model call. The review shows the selected sources, proposed destination, matching items, file alternatives, and business-context conflicts. **Review this with my AI** sends a read-only review request through the currently selected app/model/effort; unconnected apps get a prepared request. It supplies the saved review location and selected scope, not credentials. Imported instructions and excluded files are not authority or material to execute/read during that review.

**Combine & open** prepares a separate workspace, verifies copied bytes and business record/reference integrity, rechecks the originals, and opens the result. Stop cancels preparation without deleting originals. Retry reuses the same preparation and stable planned identities; a changed source requires a fresh review. A failed activation restores the previous working selection. An unfinished prepared copy can be moved to recovery rather than left as unexplained clutter.

Distinct compatible records are added using existing canonical schema/write conventions. The starting Business remains current. Divergent records and records depending on divergent copies remain preserved source material; they are never silently promoted into business truth. Source records and a portable `organization/<operation>/` review retain provenance. Imported project trees stay together; matching files may remain in those trees when needed for relative links. An exact duplicate tree or record can reuse its existing copy. AURA does not infer revision order or factual authority from a newer filesystem date. Resolve remaining business meaning through the existing update, correction, lineage, and explicit-history helpers. No new semantic merge authority is added.

Starting workspace appearance/favorites and linked locations carry across. Additional folder links retain their identities through source-qualified links. Workspace-owned custom view files are copied; an actively selected custom view inside the old workspace is retargeted to its copied location. External custom views remain external dependencies. Missing custom views use the standard interface with an explanation. No imported view is automatically executed as a new trusted connection.

**Review optional cleanup** separately checks whether originals changed, contain excluded/unaccounted material, or have known native chat, file, custom-view, startup, or scheduling dependencies. Only eligible, explicitly chosen workspace originals can move to **AURA Recovery**. Unrelated project ownership, unknown contents, credentials, directory links, and unresolved dependencies keep originals in place. The recovery location normally sits beside AURA Workspaces; another source drive uses a recovery folder on that drive, allowing a same-filesystem rename instead of an unsafe copy-and-delete move. Failure leaves the original in place. Known dependency checks cannot certify every arbitrary external program; preserve any folder still used outside AURA.

Recovery offers Restore original, a retention choice, and an explicit permanently-remove action. Default retention is **Until I remove it**. Optional 7/30/90-day expiry is processed when AURA opens, without another background service. Removal requires the recovery copy to be unchanged and the consolidated result to remain available and intact. New/changed material, recreated originals, or unresolved dependencies stop removal. A blocked expiry is disabled and kept for review. Restoring never replaces an occupied original location. Recovery permission/expiry records are machine-local and are not enabled by restoring a portable workspace backup. Native histories, provider credentials, and external schedulers keep their existing ownership.

The same operations are available without the UI:

```bash
python scripts/workspace_organization.py plan --primary "/path/to/working-workspace" --source "/path/to/another-copy" --destination "/path/to/new-workspace"
python scripts/workspace_organization.py apply <review-id>
python scripts/workspace_organization.py status <review-id>
python scripts/workspace_organization.py cleanup-preview <review-id>
python scripts/workspace_organization.py retire <review-id> "/path/to/original" --days 0
python scripts/workspace_organization.py recovery
python scripts/workspace_organization.py restore <recovery-id>
python scripts/workspace_organization.py cleanup-expired
```

`plan --business-map <json-file>` explicitly maps `source-path|business-id` to an existing or separate destination business ID; a loose project folder uses `source-path|` to select its owning business. `discard <review-id>` retires an owned, unfinished preparation to recovery. `remove <recovery-id>` is explicit permanent removal of a verified unchanged recovery copy. Operation plans and retry/retention authority stay in machine-local AURA settings. Portable reports are informational files inside the workspace. No filesystem watcher, cloud account, database, automatic account installation, or model runtime is added.

Organization failures retain the originals and provide a short cause/remedy. An interrupted directory rename is reconciled through its local recovery record. Search is bounded and expandable; unreadable recognizable workspaces stay visible as Needs attention. Disk/filename/platform incompatibilities and unavailable selected files are reported before activation. A Documents directory controlled by OneDrive/iCloud or another sync service retains that service's behavior; the destination remains visible and changeable.

- **Saved files & media:** recent files and previews, with a searchable browser for all saved work.
- **Workflows & recipes:** two separate collections, each browsable by topic and subgroup. Search can find both from the overview, with results separated by collection. Workflow instructions and recipe guidance retain their original identities and source files; categories are navigation aids.
- **Recurring tasks:** a combined view of readable native Codex and Hermes schedules, Pi `pi-schedule-prompt` jobs in the current/recently opened workspaces, and documented Google Antigravity schedule sidecars (including plugin sidecars). Discovery does not modify native files or start a model. The list refreshes every 30 seconds while the page is visible and after an AI request, without replacing forms in progress. Saved AURA monitoring plans remain separate from scheduled jobs.

Open a task and describe a change in **What would you like to change?** AURA resolves its current native identity, workspace and original session into request context, keeping the visible user request simple. The connected AI uses supported native tools/documented configuration and must read back changes. Hermes retains direct edit/pause/resume controls. A saved enabled configuration does not establish that the owning app/session/gateway is running; rows state execution requirements. Pi jobs retain their original session binding and six-field cron expressions. AURA does not transfer them into fresh sessions or run a second scheduler.

Discovery is bounded to these documented sources, not every schedule on the computer. Claude desktop task folders can remain after deletion and do not expose current timing/enabled state, so AURA does not present those folders as active tasks. Claude/cloud-only schedules and live-chat timers without an exposed shared list must still be inspected/managed through their native connection/app. Antigravity sidecar discovery follows [documented storage](https://antigravity.google/docs/sidecars); Pi storage and session requirements follow the [extension documentation](https://github.com/tintinweb/pi-schedule-prompt). Unsupported management is reported as a remaining action, never as a successful schedule.

**Settings → Adjust AI settings** opens app selection. The header keeps the notification bell and Settings. The request box shows the chosen model and effort, alongside **Chats** and **New chat**. Supported native connections reopen the exact host-owned conversation; New chat starts a separate native conversation on the next send while retaining the selected business and its saved memory. Copy-to-existing-chat connections remain handoffs. The header bell opens notifications. Settings hold appearance, the tour, API connections, business creation, folder location, and Customize this workspace.

Each area opens a detail panel and returns to the same overview. The same canonical records and persistence helpers remain authoritative.

Refresh rereads the files. Use Refresh to reread saved information. It does not claim live synchronization, complete machine-wide file discovery, verified tool access, or active scheduling simply because records exist. Unreadable canonical records produce a notice rather than silently meaning "nothing saved."

### Another agent

An agent can connect its supported non-interactive command with a small local JSON file:

```json
{
  "name": "My installed agent",
  "argv": ["/absolute/path/to/agent-command", "its-supported-stdin-option"]
}
```

Then launch:

```bash
python scripts/workspace_ui.py --agent-file /path/to/local-connection.json
```

This is a command invocation, not a provider protocol: it must accept the complete request on stdin, print only the final user-facing text to stdout, and return nonzero on failure. Tool/reasoning events belong on stderr or in the host; the view does not ingest them. Use the host's documented options, not the placeholder option above. A Windows npm command should be invoked through its actual executable/Node entry point, not a command-shell string. `argv` is executed without shell interpolation. An optional `model` string is a configured label, not independent discovery of the runtime's model.

Keep this machine-specific connection file outside the portable business files, or in the ignored `.businessos/environments/` area. Do not put keys, tokens, passwords, shell scripts, or user prompts in argv. Credentials remain with the agent. AURA does not implement OAuth, provider accounts, a router, or a general tool registry.

The local app runs one task at a time. A task can use whatever actual tools this host connection exposes; a desktop app can expose additional app-only capabilities. Its final reply is not independent proof of publication or business results. Closing a tab does not cancel its task while the local server is running. Closing/restarting the local server is not a verified cancellation or guarantee of continued host work. A chat left working is identified as needing a check in the host, rather than automatically retried. Use the host to inspect/cancel interrupted work before retrying.

## Optional API connections

**Settings → API connections** accepts keys for OpenAI, Anthropic, Google Gemini, xAI/Grok, OpenRouter, Kie AI, fal.ai, Higgsfield, and ElevenLabs. **Other service** accepts a name and documented secret environment variable. These are convenient presets, not a capability registry or a provider allowlist for ordinary AURA work. Codex is an AI app using OpenAI or its configured provider; OpenRouter is a provider gateway. OpenCode is a separate AI app.

Keys can be kept **for this session only**, or encrypted for the current Windows user using CurrentUser DPAPI in `%LOCALAPPDATA%/ViralTrac/Aura/api-keys.bin`. No plaintext fallback is used. macOS uses Keychain. Linux uses the available Secret Service keyring through `secret-tool` when a desktop D-Bus session is present. Session-only keys remain available if no protected backend exists or a keyring is locked; normal host-owned credentials continue to work. Keys never fall back to a plaintext file. Protected keys belong to the current OS user and do not travel with business files. Processes running as that Windows user may access them. Removing a key here does not revoke it at the provider or unset externally configured environment variables.

The local server supplies keys as environment variables to agent processes launched here. Requests mention only service names and variable names, never values, so the agent can use appropriate documented APIs through its real tools. Read APIs do not return saved key values. Key fields are cleared after submission and dismissal. Browser storage, preferences, business memory, command arguments and access logs do not contain saved key values. The app redacts saved values from replies it displays; the host still owns its tool execution/logging, and agents must not print secrets. Keys are not installed globally or automatically attached to an unrelated already-open app.

Saving a key makes no provider request and displays **Not verified**. The first useful operation establishes actual access. Keys do not silently rewrite app provider routing or ensure that a subscription sign-in can use API billing; the host decides its authentication precedence. Compact receipts (latest 10,000), per-chat snapshots, masked/hashed account history and alert settings stay in machine-local preferences, outside portable business memory, credentials and transcripts.
