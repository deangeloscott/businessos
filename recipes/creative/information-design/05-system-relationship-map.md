# System or relationship map

Use this when the important message is how parts connect: people, products, data, decisions, dependencies, or a flow that is difficult to see in a list.

## The idea

Choose one relationship to make visible and give every element a clear role. Show the meaningful path, exchange, dependency, or boundary first; add secondary detail only when it helps the reader answer the question. A map is useful when location, direction, or relationship carries more meaning than a sequence of steps.

## Borrowable shape

**Question or system boundary → key entities → labeled relationships → important direction or dependency → implication or next action.**

Use a legend only for symbols the reader must decode. Distinguish “sends,” “depends on,” “owns,” and “influences” instead of using one ambiguous arrow for everything. If the map becomes a web of crossings, split it into a small overview and one focused view.

## Tiny illustrative example

**Who touches an order and where feedback travels**

`Supplier ── replenishes ──> Warehouse ── fulfills ──> Customer`

`Customer ── return or question ──> Support ── pattern ──> Product team`

The labeled connections show roles and feedback paths rather than a single timeline. Use the actual ownership and handoffs for a real retailer.

## Adapt

Use real ownership, dependencies, and evidence when mapping an actual system. For a product, show the components and the path that matters to use. For a business, show who supplies, decides, receives, or supports the result. Remove relationships that do not change the reader's decision, and label uncertainty rather than presenting an inferred connection as established fact.
