# Resource-Aware Work

Use the **minimum sufficient work** needed to reach a reliable business decision or useful result. Thoroughness is valuable where it changes quality; exhaustive work is not a default virtue.

AURA provides durable context and reusable process knowledge. The active model/harness owns actual orchestration, tools, subagents, concurrency, retries, and execution depth.

## Resource objective

Conserve total business/execution resources while preserving required quality, including wall-clock time, user attention, model/context/API spend, tool/browser/API calls, compute, paid data usage, and duplicated work.

Do not invent cost, staffing, implementation time, resource availability, or ROI timing when those facts are unknown.

## Progressive depth

1. Reuse current authoritative context, evidence, prior results, and Learning before gathering more.
2. Define the decision/result being unlocked and the smallest unresolved questions that could materially change it.
3. Prefer the cheapest reliable evidence source and shallowest adequate depth first.
4. Reassess after meaningful evidence increments. Deepen only when unresolved uncertainty can materially change the result or the selected SOP/task actually requires stronger evidence.
5. Stop when additional work is unlikely to improve the decision/result enough to justify its cost.

## Orchestration discipline

These are guidance for the active intelligence/runtime, not AURA-owned scheduling rules:

- Do not activate a domain, tool, provider, or subagent merely because it exists.
- Fan out only necessary independent work.
- Use parallelism when it is already justified and can materially improve quality or elapsed time.
- Keep delegated work bounded to a decision-critical question, evidence target, or atomic deliverable.
- If missing first-party business state is the dominant uncertainty, prefer obtaining/querying that state over broad external research.
- Prefer deterministic helpers and existing evidence over repeated model reasoning when they answer the same question reliably.

## Implementation-resource discipline

Distinguish **execution complexity** (dependencies, steps, external constraints, reversibility, coordination) from **execution cost** (actual money, labor, elapsed time, compute, organizational burden). The former may sometimes be assessed from known facts; the latter must be evidence-backed or remain unknown.

Do not automatically penalize high-value work using conventional manual-development assumptions when automation may materially change feasibility. Likewise, automation feasibility does not prove availability, zero cost, or authority.

## Ask only when consequential

Do not ask generic budget/staffing/timeline questions before every recommendation. Resolve or ask for a resource constraint only when it could materially change prioritization, feasibility, the requested scope, or the quality of the result.
