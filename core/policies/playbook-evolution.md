# Playbook Evolution and System Improvement

BusinessOS can turn strong Learning into better future operating processes without confusing one successful outcome with a universal best practice.

## Promotion ladder

Use the narrowest justified level:

1. **Learning** — remember a conditional finding.
2. **Business rule** — reuse the Learning for the active business when its applicability conditions match.
3. **Process extension / local playbook** — change how this business's BusinessOS operates while preserving the canonical base.
4. **Domain/system candidate** — propose a reusable BusinessOS product change when evidence supports broader applicability.
5. **Canonical BusinessOS change** — explicit product-development work, regression-tested and released through normal change control.

Never skip levels merely because a result is exciting.

## Evolution requirements

A PlaybookEvolutionProposal must:
- cite the Learning and material evidence that motivated it;
- preserve supporting and contradicting evidence;
- state `applies_when` and `does_not_apply_when`;
- distinguish an implementation preference from an evidence-backed operating rule;
- use provider-neutral capabilities;
- define verification and rollback/deactivation;
- identify whether it augments an existing contract, creates a local playbook, or proposes a canonical revision;
- keep the narrowest valid scope.

## Adoption

Business/local adoption uses `ProcessExtension` and leaves canonical product files unchanged. The user must explicitly approve adoption.

A proposal marked `canonical_revision` is not auto-applied. It is a structured system-improvement candidate for explicit BusinessOS development. Canonical changes must preserve prior rationale/version history, regenerate derived registries/catalogs, and pass affected plus public regressions.

## Re-evaluation

Extensions and canonical candidates must be revisited when:
- new contradictory OutcomeEvaluations arrive;
- the mechanism/platform materially changes;
- applicability changes;
- a canonical release supersedes the local extension;
- the user retires the customization.

Success may strengthen maturity; contradiction may narrow, deactivate, deprecate, or supersede the process.
